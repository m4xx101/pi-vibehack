# pi-vibehack v1.0.1 + v1.1 — Design Specification

**Status:** Locked design (pending implementation plan)
**Date:** 2026-05-02
**Author:** m4xx101
**Phasing:** v1.0.1 (foot-gun fixes, days) → v1.1 (differentiation, weeks)
**Predecessor:** v1.0.0-rc1 shipped at github.com/m4xx101/pi-vibehack
**Predecessor spec:** `docs/superpowers/specs/2026-04-29-pi-vibehack-design.md` (gitignored, internal)

---

## 1. Why this exists

v1.0.0-rc1 ships a working hypothesis-tree REPL with on-the-fly tool synthesis, three-role subprocess isolation, and graphify-backed wire-layer recall. SOTA research (May 2026) confirms pi-vibehack already leads on the hardest architectural pieces — no public competitor (H-mmer/pentest-agents, XBOW, pentagi, Security Nerd, PentestAgent) has the hypothesis-tree shape, the wire-layer recall injection, or the agent-builds-tools pattern at our level of integration.

But four issues block day-1 use, and six gaps separate us from a "best in the world" harness:

**Day-1 blockers (v1.0.1):**

1. Hardcoded model names (`claude-haiku-4-5` etc) — operators on non-Anthropic providers can't install without manually rewriting frontmatter.
2. Soft deps require manual install — operators hit the "💡 install pi-super-curl" banner and never act on it.
3. No live cost telemetry — H-mmer ships this; status banner shows a count but nothing operationally useful.
4. README undersells differentiation — without the comparison story, pi-vibehack reads as "another harness."

**Differentiation gaps (v1.1):**

1. No self-evolving loop — the harness gets sharper only when the operator manually runs `/vibehack-distill`. SOTA (Harness-Evolver, March 2026) has normalized eval-driven mutation.
2. No Kali tool awareness — running on Kali, the harness is blind to the 600+ tools already on PATH.
3. No composition with operator's existing pi extensions (nicobailon's catalog, hjanuschka, etc) — pi-vibehack lives in isolation.
4. No browser-CDP verification loop — XBOW's edge against LLM-hallucinated DOM-XSS / postMessage / open-redirect.
5. No canary-based deterministic validation — XBOW kills the "did this RCE actually fire?" hallucination by retrieving planted UUIDs.
6. No `verification_advisory` mechanism — the planner has no system-level signal when a confirm should be re-checked before publishing.

This spec covers both releases as one design with internal phase boundaries because v1.1 reuses infrastructure v1.0.1 ships (`config.yaml`, soft-dep auto-install).

## 2. v1.0.1 — Foot-gun fixes (one release boundary)

### 2.1 User-configurable models via `config.yaml`

**Target:** drop hardcoded model names from `bin/lib/profile.js`. Configuration is the source of truth; frontmatter is generated from config; operator can override either layer.

**File:** `~/.pi/agent/vibehack/config.yaml`

```yaml
# Generated by `pi-vibehack install`. Edit freely; run /vibehack-config sync
# to regenerate prompt frontmatter from this file.

models:
  planner: claude-haiku-4-5
  operator: claude-opus-4-7
  reporter: claude-opus-4-7

  # Optional fallback chains (pi-prompt-template-model semantics).
  fallbacks:
    planner: [claude-sonnet-4-6, gpt-5]
    operator: [claude-opus-4-7, gpt-5]
    reporter: [claude-opus-4-7]

  # Optional per-prompt overrides — wins over `models.<role>` when set.
  per_prompt:
    vibehack-distill: claude-sonnet-4-6
    vibehack-complete: claude-opus-4-7

# Custom local-model providers — registered with pi at session_start via
# pi.registerProvider before any LLM dispatch. Reuses the documented
# pi-mono local-openai pattern.
providers:
  local-lmstudio:
    baseUrl: http://localhost:1234/v1
    apiKey: LOCAL_API_KEY
    api: openai-completions
    models:
      - id: qwen-72b-instruct
        name: Qwen 72B Instruct
        contextWindow: 32768
        maxTokens: 4096
        cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 }

# Soft-dep auto-install behavior.
auto_install:
  enabled: true                  # ask consent before installing
  allow_npm: true                # i + ii from §2.2
  fallback_on_decline: true      # decline → use fallback chain silently
```

**Lib changes:**

- New `bin/lib/config.js` — read/write/validate via small YAML parser (use `yaml` npm package or hand-rolled — config has flat structure, so hand-rolled is fine to keep dep-light).
- `bin/lib/rewrite-prompts.js` reads from `config.yaml.models` instead of the hardcoded `ROLE_PROMPTS` model lists.
- `bin/install.js` `--planner X --operator Y --reporter Z` flags write into `config.yaml`. `--profile hybrid|local|frontier` becomes a one-shot template that seeds `config.yaml.models` with sensible defaults.

**New extension hook:** `extensions/pi-vibehack/hooks/register-providers.ts`. At `session_start`, reads `config.yaml.providers` and calls `pi.registerProvider` for each. Best-effort with try/catch.

**New slash command:** `/vibehack-config sync` — re-runs `rewritePromptsForProfile` against current `config.yaml`. Operator runs after editing config or after upgrading vibehack. Hand-edits to prompt frontmatter are preserved on subsequent operations until next sync.

### 2.2 Auto-install soft deps with consent

**Scope (Q8 lock):** npm-installable only.

| Tier | Items |
|---|---|
| i — pi-extensions | `pi-super-curl`, `surf-cli`, `pi-mcp-adapter`, `memory-mode`, `handoff` |
| ii — npm tools | `playwright` (+ `npx playwright install`), `graphify` |

System tools (subfinder, nmap, etc) are NOT auto-installed in v1.0.1 — they belong to v1.1's Kali discovery path.

**UX (Q8 lock):**

**Batch at `session_start`:** the existing soft-dep banner upgrades to a prompt:

```
🌳 pi-vibehack ready · no engagement
💡 detected missing soft deps: pi-super-curl, surf-cli, graphify
   Install all? (Y/n/individual/skip-this-session)
```

If `auto_install.enabled: false`, just shows the legacy banner without prompting.

**Lazy on context need:** when the harness wants to use surf-cli for a `requires_browser: true` leaf and surf-cli isn't installed:

```
⚠ leaf n_3a needs browser automation. Install surf-cli now?
   y) install via npm
   n) fall back to playwright (if installed) or curl
   s) skip; mark leaf inconclusive
```

**Fallback chains (documented in `docs/RECIPES.md` and shown on install-failure):**

- HTTP probe: super-curl → curl → fail with clear note
- Browser: surf-cli → playwright → headless-chrome via raw CDP → fail
- Recall: graphify → grep over events.jsonl → fail-soft to "(no recall hits)"
- MCP: pi-mcp-adapter → direct MCP (high token cost warning) → fail

**File:** `extensions/pi-vibehack/lib/soft-dep-installer.ts`. Exports `detectMissingSoftDeps()`, `promptInstall(deps[])`, `installNpmGlobal(pkg)`, `fallbackFor(category)`.

### 2.3 Live cost telemetry in status banner

**Current banner:** `🌳 5 nodes · 0 confirmed · $0.003 · /vibehack-tree`

**v1.0.1 banner:**

```
🌳 5 nodes · 0 confirmed · ⚡ $0.04 (last turn) · 💰 $1.23 (eng) · /vibehack-tree
```

The `⚡ $X (last turn)` shows cost of the most recent LLM round-trip — surfaces runaway operator subprocess immediately. The `💰 $X (eng)` is the existing engagement total.

**Implementation:** `extensions/pi-vibehack/ui/status-banner.ts` adds a `lastTurnCost` calculation by reading the most recent `tool_result` event with non-zero `cost_usd`. Banner re-renders on every `tool_result` (already wired).

Optional config:

```yaml
ui:
  banner:
    show_last_turn_cost: true
    show_engagement_cost: true
    cost_warn_threshold_usd: 0.50  # turn red when last-turn cost exceeds this
```

## 3. v1.1 — Differentiation play (six features)

### 3.1 Self-evolving harness (Q2 lock: C, layered)

The headline differentiator. Two layers; same evaluator code; different triggers.

#### Layer B — engagement-driven (continuous)

**Trigger (Q4 lock D):** auto at `session_before_compact` + `/vibehack-complete`; manual via new `/vibehack-reflect` command.

**Loop:**

1. Read recent confirmed leaves from events.jsonl (since last reflection).
2. For each: extract `(situation, action, outcome, tool, recipe, specialist)` tuple.
3. Cluster by stack signature (cosine similarity ≥ 0.8 if embeddings available; string-equality fallback).
4. For each cluster of cardinality ≥ 2:
   - **Successes** → refine the recipe SKILL.md with sharper "vibehack pattern" guidance. Land in `~/.pi/agent/vibehack/skills/learned/<slug>/SKILL.md`.
   - **Failures with shared signature** → refine falsifier guidance for that hypothesis class. Land as new specialist `~/.pi/agent/vibehack/specialists/learned/<kind>/SKILL.md` with the falsifier-tells section.
   - **Successes lacking a specialist** → propose drafting one via `/vibehack-ingest --specialist <kind>` semantics under the hood.

**Outputs (Q4 lock):** only `skills/learned/` and `specialists/learned/`. Never edit shipped recipes (`skills/recipes/*` and `skills/specialists/*` are read-only territory). No proposal queue — write directly, operator can `git diff` if they version-control `~/.pi/agent/vibehack/`.

**File:** `extensions/pi-vibehack/lib/reflection.ts`. Exports `runReflection(scope: "compact"|"complete"|"manual")`. Wired into `hooks/session-before-compact.ts` and the existing `/vibehack-complete` handler. New slash command `/vibehack-reflect` invokes manually.

#### Layer A — eval-driven (on-demand)

**Trigger:** new slash command `/vibehack-evolve [--bench <name>] [--mutate]`.

**Benchmark corpus (Q3 lock B):** empty `bench/` slot. Operator populates per a contract:

```
bench/<name>/
  up.sh                     # boot the target (docker compose, vagrant, raw cmd)
  down.sh                   # tear down
  expected-findings.yaml    # declarative oracle
  README.md                 # what this bench targets
```

`expected-findings.yaml`:

```yaml
target: http://127.0.0.1:8080
class: web-app
expected_findings:
  - phase: exploit
    kind: SQLi
    surface: /login
    severity: high
    canary_token: "{{generate}}"  # optional — vibehack plants if non-null
  - phase: enum
    kind: directory-listing
    surface: /uploads/
    severity: low
allow_extras: true        # extras beyond expected_findings don't fail the bench
fail_on_missing: ["SQLi"] # but missing this one fails the run
```

We ship `bench/example/` with a documented walkthrough as the contract template.

**Evaluator loop:**

1. `up.sh` → wait for ready signal.
2. Run a fresh engagement against the bench target with the active config.
3. Collect confirmed leaves; compare against `expected_findings.yaml`.
4. For each missing required finding → log a failure case with the leaf's tree-state at engagement-end.
5. `down.sh`.
6. Pass/fail report at `bench/<name>/results/<timestamp>.md`.

**Mutation mode** (`--mutate` flag):

For each failure case:
1. Spawn a "harness-mutator" subagent in a git worktree of the operator's `~/.pi/agent/vibehack/` directory (use `git worktree add` to isolate experiments — assumes operator version-controls their data dir; if not, falls back to `cp -r` snapshot + cleanup).
2. The subagent runs as a `pi --mode json -p --no-session` subprocess like Operator/Reporter, with `model: <config.yaml.models.evolve>` (defaults to the configured Operator model, frontier-tier). Loads `subagents/vibehack-mutator.md` system prompt — discipline section: read events.jsonl, identify the insufficient recipe / specialist / system-prompt block, propose ONE focused mutation, return structured JSON `{ mutation_target, before, after, rationale }`.
3. Apply the mutation to the worktree's `skills/learned/` or `specialists/learned/` only — never touches shipped recipes.
4. Re-run the bench in that worktree.
5. **Land mutation only if:** failed bench now passes AND full regression suite (all `bench/*` runs) stays green.
6. On land: merge worktree branch, remove worktree. On reject: discard worktree, log to `bench/<name>/results/<timestamp>-rejected.md`.

**File:** `extensions/pi-vibehack/lib/evolve.ts`, `bench/example/`, new slash commands `/vibehack-evolve` and `/vibehack-reflect`.

#### Shared evaluator

Both layers reuse `lib/evaluator.ts` which compares confirmed-leaves against `expected_findings.yaml` semantics. Layer B uses the operator's actual engagement events as the implicit oracle (no expected file — the existing confirmed leaves ARE the oracle); Layer A uses the explicit `expected_findings.yaml`.

### 3.2 Kali tool auto-discovery (Q5 lock: C trigger + i breadth + iii Kali-MCP + lazy recipes)

**Trigger:** `session_start` runs `detectKaliCapabilities()` once, caches to `~/.pi/agent/vibehack/.capabilities.json`. Manual refresh via `/vibehack-rescan-kali`. Lazy refresh on miss: when the Planner asks for a tool not in the capability map, the harness probes `which <tool>` then.

**Curated tool list (~80 entries):**

`extensions/pi-vibehack/lib/kali-tools.ts` exports `KALI_TOOLS` array organized by category:

```ts
export const KALI_TOOLS = {
  recon: ["nmap", "masscan", "subfinder", "amass", "assetfinder", "httpx", "nuclei", "ffuf", "gobuster", "dirb", "wfuzz", "feroxbuster", "katana", "gau", "waybackurls", "hakrawler", "subzy", "dnsrecon", "dnsenum", "fierce", "theharvester", "shodan", "censys", "spiderfoot"],
  exploit: ["sqlmap", "metasploit-framework", "exploit-db", "searchsploit", "nikto", "wapiti", "skipfish", "wpscan", "joomscan", "droopescan", "burp-suite", "zaproxy", "ysoserial"],
  crack: ["hashcat", "john", "hydra", "medusa", "patator", "cewl", "crunch"],
  forensic: ["binwalk", "volatility", "exiftool", "foremost", "scalpel", "strings", "objdump", "radare2", "ghidra"],
  network: ["wireshark", "tcpdump", "tshark", "netcat", "socat", "responder", "impacket-tools", "crackmapexec", "evil-winrm"],
  web_api: ["curl", "httpie", "jq", "yq"],
  mobile: ["apktool", "jadx", "frida", "objection"],
  misc: ["docker", "podman", "git", "go", "python3", "node"],
};
```

For each: `detectKaliCapabilities()` runs `which <tool>` (cross-platform via `which` on POSIX, `where` on Windows). Builds map: `{ tool: { path, version?, category, available: boolean } }`.

**Kali-MCP soft companion (iii):** detect `mcp-kali-server` on PATH, or the `zebbern-kali-mcp` package. If present, register as a soft companion: banner says "💡 Kali-MCP detected — 130 tools available via MCP." When the Planner calls `vibehack_recall` for a Kali tool, the recall layer prefers Kali-MCP's catalog over our curated list. Lazy MCP discovery via `pi-mcp-adapter` if also installed (token-efficient).

**Lazy recipe generation:** first time the Planner picks a Kali tool that has no recipe in `skills/recipes/` or `skills/learned/`, the harness invokes `/vibehack-ingest <tool>` semantics under the hood. Recipe lands in `skills/learned/<tool>/SKILL.md`, hot-reloaded for the rest of the engagement.

**No bundled recipes for the 80 tools** — all lazy. Keeps package size sane; what gets used compounds in `skills/learned/`.

### 3.3 Auto-leverage existing pi extensions (Q6 lock: B)

**Detection at `session_start`:** scan `~/.pi/agent/extensions/`, `<cwd>/.pi/extensions/`, `~/.pi/agent/skills/`, `~/.pi/agent/prompts/`. Build map of installed extensions and skills.

**Six documented integrations** that fire automatically when the corresponding extension is present:

| Extension | Integration |
|---|---|
| `pi-mcp-adapter` | Replace direct MCP with the adapter's lazy-discovery proxy. Preferred for Kali-MCP and any future MCP server. |
| `memory-mode` | Defer `/vibehack-pin` to memory-mode's `/mem` if installed; otherwise use our internal AGENTS.md append. |
| `handoff` | Defer subprocess-boundary handoffs to the handoff extension; otherwise use our `pending-handoff.ts`. |
| `pi-rewind-hook` | Expose `/vibehack-rewind` that uses git checkpoints for engagement state. |
| `pi-side-chat` | Enable `/vibehack-fork` to branch the hypothesis tree into a side conversation. |
| `pi-prompt-template-model` | Already a hard dep. v1.1 makes the integration explicit: detect version, warn on incompatibility. |

**Operator's existing skills:** any `~/.pi/agent/skills/<dir>/SKILL.md` with valid frontmatter is auto-registered as a candidate for Planner `recipe_hints`. The Planner's `vibehack_expand` schema gets a fuzzy-search hint via the auto-injected `<recall>` block: "operator has these skills available: ..."

**File:** `extensions/pi-vibehack/lib/extension-detector.ts`. Detection runs once at `session_start`, results cached. Each integration is its own small module under `extensions/pi-vibehack/integrations/<name>.ts` — only loaded if the corresponding extension is detected.

### 3.4 Browser-CDP verifier (Q9 lock: D)

New specialist + soft verification advisory.

**`skills/specialists/browser-verifier/SKILL.md`** — discipline:

- Spawn headless Chrome via surf-cli or playwright fallback.
- Replay the leaf's PoC URL/payload.
- Take a screenshot to `poc/<node_id>/verification.png`.
- Capture DOM state, network requests, console messages.
- Assert the expected effect (alert dialog, popup window, redirect target, postMessage origin).
- Return structured JSON with `verified: bool`, `screenshot_ref`, `dom_assertion_ref`, `console_log_ref`.

**Browser-class kinds that trigger the soft advisory:** `DOM-XSS`, `reflected-XSS`, `stored-XSS`, `open-redirect`, `clickjacking`, `postMessage-leak`, `subdomain-takeover`.

**Soft advisory injection:** when `vibehack_confirm` fires for a browser-class kind without a prior `verification_pass` event for that node_id, the next `before_agent_start` injects:

```
<verification_advisory>
n_3a confirmed as DOM-XSS but no browser verification ran.
Either propose vibehack_propose_specialist(n_3a, "browser-verifier")
to verify in headless Chrome, or accept unverified (re-confirm via
operator override).
</verification_advisory>
```

**No hard gate.** Operator-owned decision — matches the unleashed-scope philosophy ([ADR-0007](../../adr/0007-unleashed-scope.md)).

**Event types added:** `verification_pass`, `verification_fail`, `verification_advisory`. Schema additions to `event-schema.ts`.

### 3.5 Canary primitives (Q10 lock: C)

**`extensions/pi-vibehack/lib/canary.ts`** exports:

- `plantFileCanary(engagementDir, kind)` — writes UUID-tagged file `evidence/canary-<uuid>.txt`, returns `{ uuid, ref, kind: "filesystem" }`.
- `plantHttpCallbackCanary(engagementDir, listenerPort)` — starts a tiny HTTP listener on `listenerPort`, returns `{ uuid, callback_url, kind: "http-callback" }`. Listener writes received payloads to `evidence/canary-<uuid>-callbacks.jsonl`.
- `verifyCanary(canary)` — checks if the canary was retrieved (file: hash check; HTTP: poll callbacks file). Returns `{ verified: bool, evidence_ref, retrieval_time_ms }`.
- `cleanupCanaries(engagementDir)` — called at `/vibehack-complete`; removes file canaries, stops HTTP listeners.

**Planner tool: `vibehack_canary_verify(node_id, kind)`**

Schema: `{ node_id: string, kind: "RCE" | "AFR" | "SSRF" | "blind-OOB" | "open-redirect" | "DNS" }`. Execute:
1. Plant canary appropriate for kind (filesystem for RCE/AFR, HTTP callback for SSRF/blind-OOB).
2. Append `canary_planted` event to events.jsonl with the UUID + secret.
3. Return canary metadata to the Planner — Planner then incorporates the secret into its `next_test` (e.g., curl the canary URL during the SSRF probe).
4. After Operator subprocess returns, `tool_result` hook calls `verifyCanary`. On retrieval → emit `verification_pass` event. Otherwise → `verification_advisory`.

**OOB collector for DNS/blind classes:** v1.1 doesn't bundle one. Operator brings their own (interactsh, Burp Collaborator, custom DNS server) via `/vibehack-pin canary-collector: <url>`. When `vibehack_canary_verify(node_id, kind)` is called with `kind: "DNS"` or `kind: "blind-OOB"`, the canary tool reads the pinned URL from the engagement's AGENTS.md, generates a UUID-tagged subdomain (`<uuid>.<collector-host>`), returns it to the Planner. The Operator subprocess embeds the subdomain in its `next_test`. After return, `verifyCanary` polls the collector (via the operator-supplied poll endpoint, also pinned: `canary-poll: <url>`) for retrieval. If no `canary-collector` is pinned, `vibehack_canary_verify` for OOB classes returns `{ verified: false, error: "no OOB collector pinned — see /vibehack-pin canary-collector" }`.

**v1.2 may bundle interactsh integration** as a soft companion.

### 3.6 `verification_advisory` event type + injection block

Already covered in 3.4 and 3.5 — single mechanism shared by both browser verification and canary verification.

**`before-agent-start.ts` block ordering** (extends the existing 8 blocks from v1.0):

```
event.systemPrompt
└─ persona (CLAUDE/CODEX/GEMINI/LOCAL)
└─ planner-system.md
└─ <pinned_global>     (~/.pi/agent/vibehack/AGENTS.md)
└─ <pinned_engagement> (engagementDir/AGENTS.md)
└─ <handoff_from_prior_subprocess>
└─ <operator_steer>
└─ <invariant>          (gate message)
└─ <bounds_advisory>
└─ <verification_advisory>      ← NEW in v1.1
└─ <recall>             (graphify subgraphs)
```

`<verification_advisory>` is positioned between `<bounds_advisory>` and `<recall>` because verification urgency outranks recall context — the Planner should see "you confirmed something unverified" before it gets distracted by graphify hits.

### 4.3 Schema additions

`event-schema.ts` adds three event types:

- `verification_pass`
- `verification_fail`
- `verification_advisory`
- `canary_planted`

All optional metadata; no required-field changes for existing events. Backward-compatible with v1.0.0-rc1 events.jsonl files.

### 4.4 Configuration source-of-truth shift

v1.0.0-rc1: `bin/lib/profile.js` hardcodes role → model map; `bin/lib/rewrite-prompts.js` ROLE_PROMPTS lists are hardcoded; `--profile` flag picks one of 3 fixed maps.

v1.0.1+: `~/.pi/agent/vibehack/config.yaml` is source of truth. `bin/install.js` reads it; `bin/lib/profile.js` keeps the 3 named profiles as install-time templates only (writes config.yaml from them). `rewrite-prompts.js` reads from config. Hand-editing config.yaml directly is supported.

## 5. Compatibility

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| `config.yaml` schema drift across versions | `config.js` includes a version stamp; on read, migrate forward if needed. |
| Auto-install consents fatigue operators | Single batch prompt at session_start; remember skip-this-session decision. |
| Reflection loop spams `skills/learned/` with low-quality SKILL.md | Cluster cardinality ≥ 2 minimum; mark `priority: low` for cluster-of-2; only promote to high on cluster ≥ 5. |
| Eval bench timeouts on slow targets | `up.sh` has a 60s ready-poll cap; benches that don't boot fail fast. Operator's bench/<name>/README.md documents the timeout assumption. |
| Mutation worktree merges break main branch | Mutation lands ONLY if all `bench/*` regression-pass. Otherwise worktree discarded. |
| Kali capability map staleness | Auto-refresh on miss; manual `/vibehack-rescan-kali`; cache TTL via `cached_at` field, invalidate on apt-update fingerprint mismatch. |
| Browser-verifier hallucinates "verified" without real screenshot | Verifier specialist's discipline section requires the screenshot file to exist with non-zero size; `tool_result` hook validates file ref before emitting `verification_pass`. |
| Canary HTTP listener port clash | `plantHttpCallbackCanary` picks ephemeral port via `:0`; reports actual port to caller. |
| `/vibehack-evolve --mutate` accidentally trains on a malicious target | Mutation only consumes operator's own engagement events + bench results — never untrusted target output directly. |
| Config-driven providers leak API keys to logs | API keys in `config.yaml.providers.<name>.apiKey` are the env-var NAME, not the literal key. pi-vibehack reads `process.env[apiKey]` at register time. |
| pi-vibehack's reflection clashes with `pi-prompt-template-model`'s frontmatter caching | `/vibehack-config sync` forces frontmatter regeneration after any reflection-driven recipe change that affects role assignments. |
| Soft-companion integration mid-engagement breaks | Detection at session_start only. Mid-engagement install of an integration requires `/reload`. Documented. |
| Kali-MCP catalog exceeds 128 tools | Use `pi-mcp-adapter` (PentestAgent's RAG-over-tools pattern) when count > 128. Fall back to direct MCP with token-cost warning otherwise. |
